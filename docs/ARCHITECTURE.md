# Архитектура — «Киберпанк-экономика» (MVP-базлайн)

> Снимок текущего состояния системы на 2026-06-30. Это фиксация работающего MVP
> (игра успешно проведена). Дальнейшее развитие — см. раздел [«Куда дальше»](#куда-дальше).

## 1. Что это

Экономическая ролевая игра для лагеря: у игроков есть счета (безнал + криптовалюта),
банковские карты и платёжные терминалы. Они переводят деньги, торгуют криптой на бирже
с «живым» курсом, покупают товары в магазине, читают новости. Параллельно идёт аудит и
аналитика. Роли: `PLAYER`, `BANKER`, `ADMIN`, `DEVELOPER`.

Технологически — **событийно-ориентированные микросервисы** на Spring Boot (Java),
шлюз-агрегатор, общий Kafka и Postgres (по схеме «БД-на-сервис»), SPA-фронтенд на nginx,
локальный DNS. Рассчитано на запуск **офлайн в LAN** на одном или нескольких ноутбуках.

## 4. Ключевые архитектурные решения

- **API-gateway (game-core).** Клиент общается только со шлюзом same-origin через `/api`.
  Шлюз проверяет JWT, превращает HTTP-запрос в **команду в Kafka** (`KafkaCommandGateway`)
  и ждёт ответ. Сервисы наружу напрямую не нужны (хотя порты сейчас проброшены — см.
  [SECURITY](./SECURITY.md)).
- **Событийность + Outbox.** Изменения состояния пишутся в БД вместе с записью в
  `outbox_events` в одной транзакции; публикатор асинхронно шлёт их в Kafka
  (`balance.exchanged`, `account.events` и т.д.). Это гарантирует доставку без 2PC.
- **БД-на-сервис.** Логическая изоляция данных: у каждого сервиса своя база, но физически
  один Postgres (ресурсная оптимизация для ноутбуков). Кросс-сервисные данные
  реплицируются локально (`account_snapshot` — имя/роль/статус аккаунта в banking/access/card).
- **Идемпотентность.** Банковские операции защищены `idempotency_records` (ключ + отпечаток).
- **Крипто-рынок как «физический закон».** Курс — дискретный стохастический процесс
  (mean-reverting random walk): `logReturn = drift + κ·ln(baseline/rate) + volatility·Z`,
  с админским «дрифтом» (pump/dump) и мгновенными шоками. Тики пишутся в `crypto_tick`.
- **Миграции — Flyway**, `ddl-auto: validate` (схему правят только миграции).

## 5. Потоки данных (пример: покупка крипты)

```
Браузер → nginx → gateway /api/banking/crypto/buy
   → JWT ok → Kafka command "banking.buyCrypto"
   → banking-service: списать безнал, начислить крипту по текущему курсу,
       2 проводки EXCHANGE (CASHLESS+CRYPTO) + запись в outbox  [одна транзакция]
   → outbox publisher → Kafka "balance.exchanged"
   → audit-service пишет audit_log; analytics обновляет read-model
   → ответ через gateway обратно в браузер
```

## 6. Развёртывание

Два варианта (оба — Docker Compose, офлайн-LAN):

1. **Одиночный хост (по умолчанию):** `docker-compose.yaml` — весь стек на одном ноуте.
   Запуск: `СТАРТ.cmd` или `docker compose up -d --build`. Конфиг — `.env` (см. `.env.example`).
2. **Мульти-машинный (3 ноута):** `compose.core.yaml` (Kafka+gateway), `compose.finance.yaml`
   (banking/account/access + их БД), `compose.rest.yaml` (card/terminal/market/news/audit).
   ⚠️ `analytics-service` в сплит-топологии отсутствует — аналитика доступна только в одиночном варианте.
   Конфиг — `.env` из `.env.multi.example`, ключевой параметр `CORE_HOST`. См. `DEPLOY-MULTI.md`.

Инфраструктура события: локальный DNS (`bank.lan`/`game.lan`), скрипты эксплуатации в
`deploy/balancer/` (`start-all.ps1`, `healthcheck.ps1`, `reset-data.ps1`), пошаговые
инструкции для персонала в `ИНСТРУКЦИЯ/` (сеть, IP, перенос образов, отказоустойчивость).
JVM-кучи капнуты (`Xmx128–192m`) под слабое железо.

## 7. Безопасность (кратко)

JWT на шлюзе (HS, секрет — Base64), публичные пути `/auth/**`, `/docs/**`, `/actuator/health`;
PIN-сессии для терминалов; CORS настраиваемый. **Секреты — только через `.env`** (в git не
коммитятся; compose падает без них). Подробности и бэклог харднинга — в [SECURITY.md](./SECURITY.md).

## 8. Известные ограничения / SPOF (MVP)

- **Единые точки отказа:** один Postgres, одна Kafka (RF=1). Failover между ноутами — ручной
  (см. `ИНСТРУКЦИЯ/08-ОТКАЗОУСТОЙЧИВОСТЬ.md`).
- **Сетевая поверхность:** порты сервисов (8081–8091) и Postgres (5432) проброшены на хост/LAN.
  Для продукта — закрыть, оставить только gateway+frontend.
- **Нет CI/CD:** образы собираются на машине вручную.
- **Наблюдаемость:** есть `audit`/`analytics` и actuator-метрики, но нет централизованного
  сбора логов/метрик.
- **Swagger/actuator** включены на каждом сервисе (удобно в dev, закрыть в проде).

## 9. Куда дальше

Целевая модель — **edge + cloud** (игра идёт офлайн на площадке, продукт/контроль — в облаке):

- **Фаза 0 (фундамент):** CI/CD + реестр образов, секреты в менеджере, автоматизация
  бэкап/restore, базовая наблюдаемость.
- **Фаза 1 (масштаб на событии):** перевод Compose → **k3s** (самовосстановление,
  rolling-обновления, реплики stateless-сервисов), тёплый standby Postgres.
- **Фаза 2 (продукт):** облачный control-plane (тенанты/лицензии/телеметрия/биллинг),
  edge-апплайанс с k3s и GitOps (Argo/Flux), мультиарендность и изоляция клиентов.

Полноценный облачный Kubernetes оправдан только на Фазе 2; до неё k3s-на-краю и фундамент
дают больше пользы при меньшей сложности.
