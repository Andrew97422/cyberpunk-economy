# 🛡️ 08 — Отказоустойчивость

## Честно: чего НЕЛЬЗЯ добиться на двух ноутах

Полной HA (ноль простоя при падении узла) с этой архитектурой и двумя ноутами
**не получить**. Причины принципиальные:
- **Kafka — один брокер.** Реальная отказоустойчивость Kafka требует кластера из
  3 брокеров с кворумом (нечётное число). На двух нодах кворума нет.
- **Один вход** (шлюз + фронтенд + один IP) и **одна БД на данные** — без
  репликации это единичные точки отказа.

Делать вид, что это «кластер высокой доступности», — обманывать себя. Поэтому
строим **реалистичную защиту для мероприятия**: система сама встаёт после сбоев,
данные не теряются дальше пары минут, а полное падение узла лечится вручную за
несколько минут по чёткому плану.

---

## Три уровня защиты

| Уровень | От чего спасает | Как |
|---|---|---|
| 1. Авто-восстановление | падение контейнера, перезагрузка, скачок питания | `restart: unless-stopped` + автозапуск Docker (уже есть) |
| 2. Бэкапы | потеря/повреждение данных, гибель ноута | `backup.ps1` по расписанию, копии на оба ноута |
| 3. Ручной failover | полная смерть одного ноута | поднять всё на выжившем + восстановить бэкап |

Уровень 1 уже настроен ([07](07-ЭКСПЛУАТАЦИЯ-И-ПИТАНИЕ.md)). Ниже — уровни 2 и 3.

---

## Выбор конфигурации: что надёжнее

Есть две стратегии, и они дают разный баланс «нагрузка ↔ надёжность»:

### Вариант 1. Primary + Standby (рекомендую для надёжности)
- **Ноут A (16 ГБ)** тянет **весь стек** через `docker-compose.yaml` (он для этого
  и рассчитан: один Postgres, ужатые heap'ы — влезает в 16 ГБ свободно).
- **Ноут B (8 ГБ)** — **горячий резерв**: ничего не крутит, но имеет все образы и
  получает бэкапы каждые несколько минут. Падает A → B поднимается за минуты.
- ➕ Одна точка, за которой следить; все данные в одном месте → один простой бэкап;
  чистый failover без «разъезда» данных.
- ➖ Ноут B простаивает в норме (не делит нагрузку).

### Вариант 2. Сплит (балансировщик) + аварийный план
- Оба ноута активны (как в [04](04-ЗАПУСК-НА-МЕСТЕ.md)): A = core+rest, B = finance.
- ➕ Используются оба ноута (больше запас по нагрузке).
- ➖ **Две** точки отказа вместо одной, данные на обоих ноутах → бэкапить надо оба,
  а failover сложнее.

> **Если отказоустойчивость важнее нагрузки — бери Вариант 1.** Для игры в лагере
> запас по мощности у одного 16 ГБ ноута достаточный, а простота восстановления
> важнее. Вариант 2 оправдан, только если одному ноуту реально тяжело.

## Уровень 2. Бэкапы (делаем в обоих вариантах)

### Разовый бэкап вручную
```powershell
.\deploy\balancer\backup.ps1 -PeerShare \\192.168.1.11\Backups
```
Сам находит все запущенные БД, дампит каждую, кладёт в `D:\camp-backups\<время>` и
дублирует на второй ноут (если указан `-PeerShare`).

> Для `-PeerShare` на ВТОРОМ ноуте заранее расшарь папку (напр. `Backups`) —
> так же, как в [03](03-ПЕРЕНОС-ОБРАЗОВ.md). В Варианте 1 копируй бэкап на ноут B,
> в Варианте 2 — каждый ноут копирует на другой.

### Автоматически каждые 10 минут (Планировщик задач)
PowerShell **от администратора** (подставь свой путь и IP):
```powershell
$action = New-ScheduledTaskAction -Execute "powershell.exe" `
  -Argument '-NoProfile -ExecutionPolicy Bypass -File "D:\Лагерь июнь 2026\deploy\balancer\backup.ps1" -PeerShare \\192.168.1.11\Backups'
$trigger = New-ScheduledTaskTrigger -Once -At (Get-Date) `
  -RepetitionInterval (New-TimeSpan -Minutes 10)
Register-ScheduledTask -TaskName "CampBackup" -Action $action -Trigger $trigger `
  -RunLevel Highest -Description "Бэкап БД лагеря каждые 10 минут"
```
Теперь максимум, что можно потерять при гибели ноута, — данные за последние 10 минут.
Для денежных операций можешь поставить интервал меньше (напр. 5 минут).

Проверить/удалить задачу:
```powershell
Get-ScheduledTask -TaskName "CampBackup"
Unregister-ScheduledTask -TaskName "CampBackup" -Confirm:$false
```

## Уровень 3. Failover — поднять всё на выжившем ноуте

Единый надёжный приём: **выживший ноут поднимает ВЕСЬ стек (all-in-one) и
восстанавливает последний бэкап.** Подходит для гибели любого из ноутов.

> Заранее убедись, что на ОБОИХ ноутах есть все образы (см. [03](03-ПЕРЕНОС-ОБРАЗОВ.md))
> и свежие бэкапы. Без этого failover невозможен.

### Сценарий: умер ноут A (или просто хотим перенести всё на один)

На выжившем ноуте (пусть это B):
```powershell
cd "D:\Лагерь июнь 2026"

# 1. (если на ноуте уже крутился сплит — погасить его, ДАННЫЕ останутся в томах)
docker compose -p game-camp down            # БЕЗ -v !

# 2. поднять только инфраструктуру (БД + Kafka)
docker compose -p game-camp -f docker-compose.yaml up -d postgres kafka

# 3. дождаться, пока postgres healthy
docker compose -p game-camp -f docker-compose.yaml ps

# 4. восстановить последний бэкап (подставь свежую папку)
$last = Get-ChildItem D:\camp-backups -Directory | Sort-Object Name -Desc | Select -First 1
.\deploy\balancer\restore.ps1 -BackupDir $last.FullName

# 5. поднять остальные сервисы
docker compose -p game-camp -f docker-compose.yaml up -d
```

### Чтобы устройства не меняли адрес
Самое удобное — **отдать выжившему ноуту IP погибшего**. Сначала убедись, что
мёртвый ноут ВЫКЛЮЧЕН (иначе конфликт адресов), затем на выжившем (от админа):
```powershell
# узнать индекс адаптера: Get-NetIPConfiguration | ? IPv4DefaultGateway | select InterfaceIndex
New-NetIPAddress -InterfaceIndex 12 -IPAddress 192.168.1.10 -PrefixLength 24 -DefaultGateway 192.168.1.1
```
Тогда `http://bank.lan` (и `http://192.168.1.10`) продолжит работать без объявлений.
Если возиться некогда — просто скажи персоналу новый адрес (`http://<IP_выжившего>`).

> В all-in-one сервисы общаются через внутренний `kafka:9094`, поэтому возни с
> `CORE_HOST` при failover НЕ требуется — достаточно, чтобы устройства достучались
> до фронтенда на порту 80.

### Сценарий: умер ноут B (только в Варианте 2/сплит)
Пропали сервисы `finance` (banking/account/access — деньги!). На ноуте A:
```powershell
# доставить finance на A (его БД поднимутся пустыми)
docker compose -p game-camp -f compose.finance.yaml -f deploy\balancer\compose.finance.limits.yaml up -d
# восстановить деньги из последнего бэкапа
$last = Get-ChildItem D:\camp-backups -Directory | Sort-Object Name -Desc | Select -First 1
.\deploy\balancer\restore.ps1 -BackupDir $last.FullName
```
> Поэтому в Варианте 2 критично, чтобы бэкапы ноута B регулярно копировались на A.

## Мониторинг — замечать сбой быстро

```powershell
.\deploy\balancer\healthcheck.ps1 -EntryIp 192.168.1.10 -PeerIp 192.168.1.11
```
Показывает статус контейнеров, живость связки шлюз+Kafka и доступность второго
ноута. Чем раньше заметишь проблему, тем быстрее failover.

- [ ] На ОБОИХ ноутах есть все образы (failover невозможен без этого).
- [ ] Настроен авто-бэкап (Планировщик, каждые 5–10 мин).
- [ ] Бэкапы копируются на ВТОРОЙ ноут (`-PeerShare`), а не только локально.
- [ ] Хотя бы раз провёл «учебный» failover дома и убедился, что данные встают.
- [ ] Знаешь, как отдать IP погибшего ноута выжившему.
- [ ] Сон/обновления отключены ([07](07-ЭКСПЛУАТАЦИЯ-И-ПИТАНИЕ.md)) — иначе «отказ»
      устроишь себе сам.

> ⚠️ Бэкап, который ни разу не восстанавливали, — это не бэкап. Проверь
> восстановление ДОМА, пока есть время.
